# 翻譯工作單

> **錄音提交：** 請參閱[私人 Drive 錄音提交指南（英語）](../VOICE_SUBMISSIONS.md)。上傳並勾選後，由另一位審核者試聽並核准，再建立僅包含提交清單的 PR。音訊保存在 Drive 中。下文說明台詞與 UI 文字的翻譯流程。

Google 試算表用來填寫和審閱譯文。GitHub 工作單用來保留工作範圍、記錄負責人，並控制通過審核的譯文何時產生提取請求（PR）。

**修改試算表不會自動更新儲存庫或遊戲。** 機器人會將經過審核的特定快照匯入 PR。維護者仍須審查並合併該 PR，再由開發者將譯文納入遊戲組建版本。

本流程適用於現有 UI 文字及配音台詞的文字翻譯。錄音、試音、新台詞草稿，以及尚無來源文字 ID 的內容，須依各自的準備流程處理。

社群翻譯必須透過工作單機器人建立交付 PR。手動建立翻譯 PR 無法跳過工作保留和快照審核。

本文以[英文指南](../CONTRIBUTION_WORKFLOW.md)為參考。歡迎母語使用者回報不自然或不清楚的表述；本文不代表已通過母語審校。

閱讀指南或列入報名名單，不等於已保留工作或已核准提交。請以機器人的保留確認為準。

請將指令以留言形式發到已分配的 GitHub 工作單議題中。核准時，從機器人的預覽回覆中複製 `Digest:` 後的全部 64 個字元，只替換範例中的 `<sha256>`。指令保持英文，不要直接送出預留位置文字 `<sha256>`。

## 角色與職責

| 角色 | 職責 |
| --- | --- |
| 貢獻者 | 在試算表中完成分配給自己的翻譯，並要求產生預覽。 |
| 審閱者 | 檢查語境、術語、措辭是否自然，以及預覽中的具體內容，並使用自己的 GitHub 帳號核准該快照的摘要值。 |
| 維護者 | 建立或核對工作單、保留工作範圍、管理試算表權限、審查產生的 PR，並將其合併。 |

貢獻者和審閱者必須是不同的 GitHub 使用者。機器人只驗證身分和檔案結構，不會判斷譯文是否自然。

貢獻者可以全程在 Google 試算表中完成翻譯，無須安裝 Git、複製儲存庫或自行建立 PR。核准預覽的人需要 GitHub 帳號。如果貢獻者不熟悉 GitHub 留言，維護者可以代為要求預覽。

## 1. 先議定一個小任務

透過現有的譯者申請議題或 Discord 支援工單報名。開始前，由維護者與參與者確定語言、貢獻者、審閱者及工作範圍。

私人報名表只用來整理申請，不是工作保留登記表。其中的內容不應複製到公開的 GitHub 議題中。

建立一個 [**Translation work order** 議題](https://github.com/Epheria/Ebbtide-Community/issues/new?template=work_order.yml)，填寫以下欄位。表單欄位名稱保留英文：

| 欄位 | 填寫內容 |
| --- | --- |
| Kind | `ui` 或 `voice-text`。 |
| Locale | 儲存庫使用的語言代碼，例如 `ja`、`ru` 或 `pt-BR`。 |
| Table or voice role | 現有來源文字表或配音角色的名稱，不含路徑或 `.csv` 副檔名。 |
| Contributor | 一位貢獻者的 GitHub 使用者名稱，不含 `@`。 |
| Reviewer | 另一位使用者的 GitHub 使用者名稱，不含 `@`。 |
| Spreadsheet URL | 本任務使用的 Google 試算表檔案網址。 |
| Sheet tab | 工作表分頁的完整名稱，必須完全一致。 |
| First key | 工作範圍內第一個現有來源文字鍵。 |
| Last key | 工作範圍內最後一個現有來源文字鍵。 |

工作範圍依**儲存庫標準來源檔案中的順序**決定，包含首尾兩個鍵，不依字母順序或試算表目前的列順序決定。每單最多包含 200 個鍵。對於配音台詞，鍵為腳本中的 `file` 識別碼，不含 `.wav` 或 `.flac`。

每張工作單只對應一種語言，以及一張 UI 表或一個配音角色。範圍較小更方便審閱，也能減少遊戲文字變動時的衝突。

## 2. 保留成功後再開始翻譯

維護者在議題中留言：

```text
/work assign
```

等待機器人確認保留成功。填寫議題、關閉議題或在試算表中填入姓名，都不會保留或釋出工作。

機器人將分配紀錄寫入 `community-work-state` 分支的 `registry.json`，並固定議題欄位、具體來源文字鍵和來源檔案雜湊值。如果相同類型、語言、UI 表或配音角色已有其他進行中的任務占用相同範圍，機器人會拒絕重疊分配。不同語言可以同時翻譯相同的來源文字鍵。

之後修改議題內文，不會改變現有分配。若須變更範圍、試算表檔案、貢獻者或審閱者，請維護者釋出舊任務，再建立修正後的工作保留。

## 3. 在試算表中填寫譯文

維護者提供目前的來源文字列，並授予相關人員編輯權限。機器人必須能在未登入 Google 的情況下讀取試算表，但編輯權限應只授予本任務的參與者。

保護來源文字鍵及英文原文欄，只允許貢獻者編輯所需的輸入儲存格。請勿啟用「知道連結的任何人皆可編輯」。試算表權限和受保護範圍須手動設定；GitHub 機器人不會管理 Google 權限。

UI 翻譯須保留以下四個 CSV 欄名：

```text
key,en,translation,status
```

該分頁只能包含工作單中指定的那張 UI 表的資料列。彙整多張表的總表可作為參考，不能直接作為工作單的匯入分頁。機器人會將所選分頁中所有已填入資料的列與指定來源文字表核對。

填寫 `translation`，並沿用現有的 `status` 值。UI 列只有在 `status` 留空時才可匯入。標為 `review` 或 `outdated` 的列會暫緩處理。狀態留空本身不代表核准，仍須完成下方獨立的審核步驟。

配音台詞的文字翻譯須依此順序保留以下欄名，不可更改：

```text
Take file,English source,Translation,Review status,Notes,Role,Situation,Tone,Current voices,Source readiness,Source file,Source record
```

現有的日文、俄文及韓文配音分頁採用此格式。機器人先依 `Role` 的精確值篩選，例如 `carrier_jet_pilot`，再選取已保留的 `Take file` 鍵。填寫 `Translation`，並將通過審閱的列在 `Review status` 中標為 `Approved`。

通過審核的文字會以 `key,en,translation,status` 格式寫入 `voice/translations/<locale>/<role>.csv`。此操作只匯入台詞文字，不代表錄音已獲核准，也不代表某句草稿台詞已在遊戲中實作。

兩類任務均須遵守以下要求：

- 保留預留位置符號、必要標籤和換行標記。
- 保持來源文字鍵和英文原文與所分配的來源文字完全一致。
- 預覽前，完成保留範圍內的每一條翻譯。
- 將試算表儲存格當作文字使用，不要用公式擷取或組合譯文。
- 不要將私人聯絡方式、工單訊息或試音檔案放入工作試算表或公開議題。

如果任務範圍太大、無法完成，請與維護者拆分或釋出任務，不要讓未完成的工作長期占用保留範圍。

## 4. 要求並審閱預覽

已分配的貢獻者、審閱者或維護者在議題中留言：

```text
/work preview
```

機器人透過 Google 試算表公開的 CSV 匯出讀取保留範圍，檢查固定的來源文字、狀態、譯文是否為空，以及必要變數。它也會記錄儲存庫目前的譯文，以便之後核准時辨識其他人是否改動過目標內容。

機器人會儲存不可修改的快照，並發布其 SHA-256 摘要值及審閱連結。請審閱快照本身，不要只看議題摘要或即時試算表。快照才是預計提交的內容；產生預覽後，即時試算表仍可能變更。

審閱者須檢查：

- 含義和語境是否與英文原文一致。
- 措辭是否自然，術語是否與詞彙表一致。
- 相關 UI 的文字長度或台詞唸出的效果。
- 預留位置符號的位置、標籤和換行。

如須修改，請更新試算表，再執行一次 `/work preview`，並使用新的摘要值。預覽連結只是待審閱的資料，不代表獲准合併。

## 5. 核准指定快照

只有已分配的審閱者可以留言以下指令，並將範例替換為預覽中完整的摘要值：

```text
/work approve <sha256>
```

機器人驗證審閱者身分，再次讀取試算表，並要求內容與獲准快照一致。它也會檢查來源文字和儲存庫目標內容在預覽後是否變更。試算表或目標檔案有變動時，需要重新預覽。標準來源文字表有變動時，則須重新分配任務，詳見下文。

檢查成功後，機器人會使用已驗證的檔案建立 PR，**不會自動合併**。試算表中的 `Approved`，或一般的「沒問題」留言，都不能代替此指令。

維護者審查差異，並在檢查通過後合併 PR。在此之前，工作仍保持保留狀態。關於預計提交檔案的討論應集中於該 PR，方便追蹤最終修改。

受信任的 `reviewed-sheet` 政策會對照工作單紀錄和獲准快照檢查 PR。它將 PR 檔案當作資料讀取，執行的是受信任的預設分支程式碼。手動建立的翻譯 PR、被改動的交付檔案，或夾帶額外檔案的獲准交付，都會遭到拒絕。核准後修改機器人分支，無法將已審閱快照換成其他文字。

## 6. 完成或釋出工作保留

PR 合併或關閉後，執行：

```text
/work sync
```

此指令會同步登記狀態：已合併的 PR 會使任務完成；已關閉但未合併的 PR 會釋出工作。請查看機器人的確認，不要認為議題狀態變更就表示保留狀態已改變。

GitHub 發出 PR 關閉事件時，協調工作流程也會同步已登記的機器人 PR。如果自動同步未完成，可用 `/work sync` 手動處理。對於仍開啟的 PR，`/work sync` 也會重新要求執行檢查；若 PR 建立後的檢查派送失敗，可使用此指令。

若尚未建立 PR，維護者可留言以下指令取消分配：

```text
/work release
```

若已有開啟的 PR，必須先關閉，再釋出工作。這樣可避免相同保留範圍出現兩份同時有效的提交。

## 指令速查

| 指令 | 可執行者 | 結果 |
| --- | --- | --- |
| `/work assign` | 維護者 | 固定工作單內容，並保留來源文字範圍。 |
| `/work preview` | 已分配的貢獻者、審閱者或維護者 | 驗證並儲存供審閱的快照。 |
| `/work approve <sha256>` | 已分配的審閱者 | 再次核對指定快照，並建立 PR。 |
| `/work release` | 維護者 | 在沒有開啟的 PR 時取消保留。 |
| `/work sync` | 維護者 | 將已合併或關閉的 PR 狀態同步至登記表。 |

## 遊戲文字變動時

無須為每個遊戲版本建立新試算表。穩定的來源文字 ID 能讓現有譯文在一般更新後繼續保留。請透過儲存庫的來源文字更新流程新增資料列，並依[在地化說明](../../localization/README.md)將原文已變更的譯文標為待複審。

分配任務時，固定的是其所在整張 UI 表或整個配音角色的來源文字快照。如果核准前，該標準來源文字表發生任何變更，即使保留鍵本身未變，機器人也會停止匯入。維護者須關閉任何已開啟的交付 PR、釋出舊工作單、更新試算表中的來源文字列，再建立一張**新的工作單議題**。保留志工已完成的譯文，並對照更新後的來源文字檢查，再由審閱者審閱新的預覽。其他來源文字表的任務可以繼續。

沒有真實來源文字 ID 的規劃列尚不能匯入。請先留在規劃區，等開發者新增正式來源文字項目。不要自行編造正式 ID，也不要只為了夾帶未來內容而上傳整張試算表。

## 維護者設定與限制

工作單程式碼及議題表單合併至預設分支後，才能啟用此工作流程。狀態登記表儲存在 `community-work-state` 分支；指令執行期間不要手動修改。

工作流程使用儲存庫的 `GITHUB_TOKEN`，並需要相應的儲存庫權限，才能寫入狀態及機器人分支、在議題中留言及建立 PR。它不需要 Google OAuth 連線或個人存取權杖。Google 存取僅限讀取公開的 CSV 匯出。

在儲存庫的 Actions 設定中，允許 GitHub Actions 建立 PR。機器人的身分必須與人工語言審閱者分開。

不要假設機器人建立的 PR 會自動觸發一般的 `pull_request` 工作流程。匯入器會在建立 PR 前驗證候選檔案，並明確派送機器人分支上的 `check.yml`，以及受信任預設分支上的 `delivery-policy.yml`，後者使用該 PR 編號。

保護預設分支，並將 `check` 和 `reviewed-sheet` 提交狀態均設為必要檢查。政策工作流程必須有權限發布該狀態。合併前確認兩項檢查皆成功；僅新增工作流程檔案，不會自動設定儲存庫的分支保護。

工作登記表防止重複分配；必要的交付政策防止手動翻譯 PR 跳過分配流程。兩者都不會管理 Google 試算表的編輯權限。請限制編輯權限，並保護來源文字欄。

自動檢查負責找出結構問題和過期內容。翻譯品質、語境、貢獻者條款及是否適合遊戲，仍由人工審閱負責。
