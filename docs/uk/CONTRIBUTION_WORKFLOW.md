# Як працювати над перекладом

> **Подання записів:** див. [посібник із записів у приватному Drive (англійською)](../VOICE_SUBMISSIONS.md). Після завантаження та позначення прапорців інша людина прослуховує й схвалює файли. Тоді створюється PR лише зі списком подання. Аудіо залишається у Drive. Нижче описано переклад тексту.

У разі розбіжностей орієнтуйтеся на [англійський оригінал](../CONTRIBUTION_WORKFLOW.md). Виправлення від носіїв української вітаються. Команди, назви полів, заголовки CSV і значення станів залишено англійською: бот розпізнає їх лише в точному написанні.

Команди з цього посібника надсилайте як коментарі до issue призначеного завдання на GitHub. Залишайте англійський текст команди без змін.

## Загальний принцип

Переклад пишуть і перевіряють у Google Таблицях. Завдання в GitHub закріплює обсяг роботи, визначає відповідальних і керує створенням pull request (PR) із погодженої копії.

**Редагування таблиці не оновлює репозиторій або гру.** Бот переносить у PR конкретну перевірену копію. Відповідальний за репозиторій ще має переглянути й об'єднати PR, а розробник — додати результат до збірки гри.

Цей процес охоплює наявні рядки інтерфейсу та письмові переклади сценаріїв озвучення. Аудіозаписи, проби голосу, чернетки нових реплік і текст без вихідного ID готують окремо. Спільнота подає переклади через бота: створений вручну PR не може обійти закріплення роботи й схвалення копії.

## Ролі

- **Виконавець:** перекладає призначені рядки й запитує попередній перегляд.
- **Рецензент:** перевіряє контекст, терміни, природність і саму копію; схвалює її хеш зі свого облікового запису GitHub.
- **Відповідальний за репозиторій (maintainer):** погоджує завдання, закріплює діапазон, налаштовує доступ до таблиці, перевіряє та об'єднує PR.

Виконавець і рецензент мають бути різними користувачами GitHub. Бот перевіряє користувачів і структуру файлів, але не визначає якість мови. Для самого перекладу достатньо Google Таблиць: установлювати Git, клонувати репозиторій або самостійно відкривати PR не потрібно. Той, хто схвалює копію, мусить мати обліковий запис GitHub. Якщо виконавцю потрібна допомога з коментарями GitHub, maintainer може запитати перегляд від його імені.

## 1. Погодьте невелике завдання

Подайте заявку через наявну issue для перекладачів або тікет підтримки в Discord. До початку роботи maintainer погоджує мову, виконавця, рецензента й обсяг. Приватна таблиця заявок — лише черга звернень, а не реєстр закріпленої роботи. Не копіюйте її вміст у публічні issue.

Створіть issue [Translation work order](https://github.com/Epheria/Ebbtide-Community/issues/new?template=work_order.yml). Англійські назви полів не змінюйте:

| Поле | Що вказати |
| --- | --- |
| Kind | `ui` або `voice-text` |
| Locale | Код мови в репозиторії, наприклад `uk`, `ja` чи `pt-BR` |
| Table or voice role | Назву наявної вихідної таблиці або ролі без шляху та розширення `.csv` |
| Contributor | Один логін GitHub без `@` |
| Reviewer | Інший логін GitHub без `@` |
| Spreadsheet URL | Адресу документа Google Таблиць для цього завдання |
| Sheet tab | Точну назву вкладки |
| First key | Перший наявний вихідний ключ діапазону |
| Last key | Останній наявний вихідний ключ діапазону |

Обидві межі входять до діапазону. Використовується **порядок рядків у канонічному вихідному файлі**, а не алфавітний порядок і не поточне сортування таблиці. Максимум — 200 ключів. Для сценаріїв ключ — це ідентифікатор `file` без `.wav` чи `.flac`.

Одне завдання охоплює одну мову й одну таблицю інтерфейсу або голосову роль. Короткий діапазон легше перевірити; він також зменшує кількість конфліктів під час змін у грі.

## 2. Закріпіть роботу до початку перекладу

Maintainer залишає в issue коментар:

```text
/work assign
```

Дочекайтеся підтвердження бота. Заповнення чи закриття issue або ім'я в таблиці самі по собі не закріплюють і не звільняють роботу.

Бот записує призначення в `registry.json` у гілці `community-work-state`. Він фіксує поля issue, точні ключі та хеш джерела. Перетин з іншим активним завданням того самого типу, мови й таблиці або ролі буде відхилено. Різні мови можуть працювати над однаковими ключами.

Редагування опису issue не змінює активне призначення. Якщо треба змінити діапазон, документ, виконавця або рецензента, попросіть maintainer звільнити його та оформити правильне призначення.

## 3. Працюйте в таблиці

Maintainer надає актуальні вихідні рядки й доступ на редагування призначеним людям. Бот має читати документ без входу в Google, але право редагування слід обмежити учасниками завдання. Захистіть ключі й англійський текст; відкривайте лише потрібні поля введення. Не вмикайте редагування для всіх, хто має посилання. Доступи й захищені діапазони налаштовують вручну: бот GitHub не керує дозволами Google.

Для інтерфейсу збережіть чотири стовпці:

```text
key,en,translation,status
```

Вкладка має містити рядки лише однієї таблиці інтерфейсу, вказаної в завданні. Зведений список із кількох таблиць придатний для довідки, а не для прямого імпорту. Бот перевіряє всі заповнені рядки вибраної вкладки за відповідною вихідною таблицею.

Редагуйте `translation` і використовуйте наявні значення `status`. Рядок інтерфейсу готовий до імпорту лише з порожнім `status`. Значення `review` і `outdated` блокують імпорт. Порожній стан не означає схвалення — потрібна окрема перевірка.

Для письмових перекладів озвучення потрібні такі точні заголовки в цьому порядку:

```text
Take file,English source,Translation,Review status,Notes,Role,Situation,Tone,Current voices,Source readiness,Source file,Source record
```

Наявні японська, російська й корейська вкладки вже мають цю структуру. Бот фільтрує рядки за точним значенням `Role`, наприклад `carrier_jet_pilot`, а потім вибирає закріплені ключі `Take file`. Заповніть `Translation` і після перевірки тексту встановіть `Approved` у `Review status`.

Схвалений текст потрапляє в `voice/translations/<locale>/<role>.csv` зі стовпцями `key,en,translation,status`. Це імпорт лише письмових реплік: він не схвалює аудіозапис і не підтверджує, що чернеткова репліка вже працює у грі.

Для обох типів завдань:

- Зберігайте змінні, обов'язкові теги й позначення перенесення рядків.
- Не змінюйте вихідні ключі та англійський текст призначеного джерела.
- Заповніть увесь закріплений діапазон до запиту перегляду.
- Використовуйте текстові значення, а не формули для отримання чи створення перекладу.
- Не додавайте приватні контакти, повідомлення з тікетів або проби голосу в робочий документ чи issue.

Якщо завдання завелике, домовтеся про поділ або звільнення з maintainer. Не залишайте незавершену роботу закріпленою безстроково.

## 4. Запитайте та перевірте попередній перегляд

Призначений виконавець, призначений рецензент або maintainer коментує:

```text
/work preview
```

Бот читає закріплений діапазон із публічного CSV-експорту Google Таблиць. Він перевіряє зафіксоване джерело, стани, непорожні переклади й обов'язкові змінні. Також перевіряє поточний переклад у репозиторії, щоб пізніше виявити сторонні зміни.

Бот зберігає незмінну копію й публікує посилання та її хеш SHA-256. Перевіряйте **саме цю копію**, а не лише підсумок issue чи живу таблицю: після перегляду таблиця може змінитися. Рецензент перевіряє зміст і контекст, природність і термінологію, довжину в інтерфейсі чи зручність вимови, розташування змінних, теги та перенесення.

Якщо потрібні правки, змініть таблицю й знову виконайте `/work preview`. Використовуйте новий хеш. Посилання на перегляд — матеріал для перевірки, а не дозвіл об'єднати PR.

## 5. Схваліть точну копію

Лише призначений рецензент залишає команду, замінивши позначення повним хешем із 64 символів:

```text
/work approve <sha256>
```

Скопіюйте всі 64 символи після `Digest:` у відповіді бота з попереднім переглядом і замініть ними лише `<sha256>` у команді. Не перекладайте команду й не надсилайте позначення `<sha256>` буквально.

Бот перевіряє особу рецензента та знову читає таблицю: вона має збігатися зі схваленою копією. Він також перевіряє, що джерело й цільовий вміст репозиторію не змінилися після перегляду. Зміна таблиці чи цільового файлу потребує нового перегляду. Зміна канонічної вихідної таблиці потребує нового завдання, як описано нижче.

Після успішної перевірки бот відкриває PR із перевіреними файлами, але **не об'єднує його**. Значення `Approved` у таблиці чи звичайний схвальний коментар не замінюють команду. Робота лишається закріпленою, поки maintainer не перегляне diff і не об'єднає PR після успішних перевірок. Обговорюйте запропоновані файли в самому PR.

Довірена політика `reviewed-sheet` звіряє PR із записаним завданням та схваленою копією. Вона читає файли PR як дані та виконує довірений код із основної гілки. Вона відхиляє ручний PR перекладу, змінений файл подання або додаткові файли в поданні. Редагування гілки бота після схвалення не дозволяє підмінити перевірений текст.

## 6. Завершіть або звільніть призначення

Після об'єднання або закриття PR maintainer виконує:

```text
/work sync
```

Об'єднаний PR завершує завдання; закритий без об'єднання — звільняє його. Перевірте підтвердження бота, а не лише стан issue. Координатор також узгоджує стан, коли GitHub надсилає подію закриття записаного PR бота. Якщо автоматичний запуск не завершився, виконайте команду вручну. Для відкритого PR `/work sync` повторно запитує перевірки, якщо їх не вдалося запустити після створення PR.

Щоб скасувати призначення без PR, maintainer коментує:

```text
/work release
```

Якщо PR відкритий, спочатку його треба закрити. Це не дозволяє мати два активні подання одного закріпленого діапазону.

| Команда | Хто виконує | Результат |
| --- | --- | --- |
| `/work assign` | Maintainer | Фіксує завдання й закріплює діапазон. |
| `/work preview` | Призначений виконавець, рецензент або maintainer | Перевіряє та зберігає копію для рецензування. |
| `/work approve <sha256>` | Призначений рецензент | Повторно звіряє точну копію й відкриває PR. |
| `/work release` | Maintainer | Скасовує призначення, якщо немає відкритого PR. |
| `/work sync` | Maintainer | Узгоджує стан PR із реєстром. |

## Коли змінюється текст гри

Не створюйте новий документ для кожної версії гри. Стабільні ID дозволяють зберегти переклади. Додавайте нові рядки через процес оновлення джерел у репозиторії й позначайте змінені переклади для перевірки за [посібником із локалізації](../../localization/README.md).

Завдання фіксує джерело **всієї таблиці інтерфейсу або голосової ролі**. Якщо канонічна таблиця зміниться до схвалення, бот зупинить імпорт, навіть якщо закріплені ключі не змінилися. Maintainer закриває відкритий PR подання, звільняє старе завдання, оновлює вихідні рядки в таблиці й відкриває **нову issue завдання**. Збережіть переклад волонтера та звірте його з оновленим джерелом; рецензент має переглянути нову копію. Завдання з інших вихідних таблиць можуть тривати.

Рядок планування без реального ID ще не готовий до цього імпорту. Залишайте його в плануванні, доки розробник не додасть канонічний запис. Не вигадуйте робочі ID й не завантажуйте весь документ заради майбутнього вмісту.

## Налаштування й обмеження для maintainer

- Вмикайте процес лише після об'єднання коду та форми issue з основною гілкою. Не редагуйте реєстр `community-work-state` вручну під час активних команд.
- Процес використовує `GITHUB_TOKEN` репозиторію з дозволами на запис стану й гілки бота, коментарі до issue та створення PR. Google OAuth і особистий токен не потрібні. Доступ до Google обмежений читанням публічного CSV.
- У налаштуваннях Actions дозвольте GitHub Actions створювати PR. Облікові записи бота й людини-рецензента мають бути окремими.
- Не покладайтеся на те, що PR бота запустить звичайні процеси `pull_request`. Імпортер перевіряє файли до створення PR, а потім явно запускає `check.yml` для гілки бота та `delivery-policy.yml` з довіреної основної гілки для відповідного номера PR.
- Захистіть основну гілку обома обов'язковими перевірками: `check` та станом коміту `reviewed-sheet`. Процес політики мусить мати право публікувати цей стан. Перед об'єднанням переконайтеся в успіху обох: самі файли процесів не вмикають захист гілки.
- Реєстр запобігає перетину завдань, а обов'язкова політика — обходу через ручні PR перекладів. Вони не керують правами Google Таблиць: обмежте редагування й захистіть джерело.

Автоматичні перевірки знаходять структурні помилки та застарілі дані. Якість перекладу, контекст, умови участі й придатність для гри залишаються відповідальністю людей.
