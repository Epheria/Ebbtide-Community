# วิธีทำงานแปลร่วมกัน

> **การส่งไฟล์เสียง:** ดู[คู่มือส่งเสียงผ่าน Drive ส่วนตัว (ภาษาอังกฤษ)](../VOICE_SUBMISSIONS.md) หลังอัปโหลดและทำเครื่องหมายในช่อง ผู้ตรวจอีกคนต้องฟังและอนุมัติก่อน จึงจะสร้าง PR ที่มีเฉพาะรายการส่งงาน ไฟล์เสียงยังอยู่ใน Drive คำแนะนำด้านล่างเป็นขั้นตอนการแปลข้อความ

หากคำอธิบายต่างกัน ให้ยึด[คู่มือภาษาอังกฤษ](../CONTRIBUTION_WORKFLOW.md)เป็นหลัก ยินดีรับคำแนะนำเรื่องสำนวนจากผู้ใช้ภาษาไทยเป็นภาษาแม่ คำสั่ง ชื่อช่องใน issue หัวคอลัมน์ CSV และค่าสถานะยังเป็นภาษาอังกฤษ เพราะบอตต้องอ่านให้ตรงทุกตัวอักษร

พิมพ์คำสั่งในคู่มือนี้เป็นคอมเมนต์ใน issue ใบงาน GitHub ที่ได้รับมอบหมาย คงคำสั่งภาษาอังกฤษให้ตรงกับตัวอย่าง

## ภาพรวม

เขียนและตรวจคำแปลใน Google ชีต ส่วนใบงานบน GitHub ใช้จองขอบเขต ระบุผู้รับผิดชอบ และควบคุมการนำสำเนาที่อนุมัติแล้วไปสร้าง pull request (PR)

**การแก้ชีตไม่ได้อัปเดตคลัง GitHub หรือเกมทันที** บอตจะนำสำเนาที่ตรวจแล้วตรงตามฉบับนั้นไปสร้าง PR ผู้ดูแลโครงการยังต้องตรวจและรวม PR ก่อน จากนั้นผู้พัฒนาจึงนำผลไปใส่ในเกมรุ่นถัดไป

ระบบนี้ใช้กับข้อความหน้าจอที่มีอยู่แล้วและคำแปลบทพูดแบบข้อความเท่านั้น ไฟล์เสียง ออดิชัน ร่างบทพูดใหม่ และข้อความที่ยังไม่มี ID ต้นฉบับต้องเตรียมแยกกัน งานแปลของชุมชนต้องส่งผ่านบอต การเปิด PR แปลเองไม่สามารถข้ามขั้นตอนจองงานและอนุมัติสำเนาได้

## ใครรับผิดชอบอะไร

- **ผู้แปล:** แปลช่วงที่ได้รับมอบหมายในชีตและขอสำเนาตัวอย่างเพื่อตรวจ
- **ผู้ตรวจภาษา:** ตรวจบริบท ศัพท์ ความเป็นธรรมชาติ และสำเนาตัวอย่างฉบับนั้น แล้วอนุมัติค่าแฮชด้วยบัญชี GitHub ของตนเอง
- **ผู้ดูแลโครงการ (maintainer):** ตกลงใบงาน จองช่วงงาน จัดการสิทธิ์ชีต ตรวจ PR และรวมเข้าคลัง

ผู้แปลกับผู้ตรวจต้องเป็นผู้ใช้ GitHub คนละบัญชี บอตตรวจตัวตนและโครงสร้างไฟล์ แต่ไม่ตัดสินว่าคำแปลเป็นธรรมชาติหรือไม่ ผู้แปลทำงานใน Google ชีตอย่างเดียวได้ ไม่ต้องติดตั้ง Git โคลนคลัง หรือเปิด PR เอง ผู้อนุมัติสำเนาต้องมีบัญชี GitHub หากผู้แปลไม่สะดวกใช้คอมเมนต์บน GitHub ผู้ดูแลสามารถขอสำเนาตัวอย่างแทนได้

## 1. ตกลงงานขนาดเล็กก่อน

สมัครผ่าน issue สำหรับผู้แปลหรือทิกเก็ตช่วยเหลือใน Discord ผู้ดูแลจะตกลงภาษา ผู้แปล ผู้ตรวจ และขอบเขตก่อนเริ่มงาน ชีตรายชื่อผู้สมัครแบบส่วนตัวใช้รับคำขอเท่านั้น ไม่ใช่ทะเบียนจองงาน และไม่ควรคัดลอกข้อมูลในนั้นไปใส่ issue สาธารณะ

เปิด issue แบบ [Translation work order](https://github.com/Epheria/Ebbtide-Community/issues/new?template=work_order.yml) โดยคงชื่อช่องภาษาอังกฤษดังนี้:

| ช่อง | ข้อมูลที่ต้องใส่ |
| --- | --- |
| Kind | `ui` หรือ `voice-text` |
| Locale | รหัสภาษาในคลัง เช่น `th`, `ja` หรือ `pt-BR` |
| Table or voice role | ชื่อตารางต้นฉบับหรือบทบาทเสียงที่มีอยู่ ไม่ใส่พาธหรือนามสกุล `.csv` |
| Contributor | ชื่อผู้ใช้ GitHub หนึ่งคน ไม่ใส่ `@` |
| Reviewer | ชื่อผู้ใช้ GitHub อีกคนที่ไม่ใช่ผู้แปล ไม่ใส่ `@` |
| Spreadsheet URL | ที่อยู่เอกสาร Google ชีตที่ใช้ในงานนี้ |
| Sheet tab | ชื่อแท็บในชีตแบบตรงทุกตัวอักษร |
| First key | คีย์ต้นฉบับที่มีอยู่ตัวแรกที่ต้องการรวม |
| Last key | คีย์ต้นฉบับที่มีอยู่ตัวสุดท้ายที่ต้องการรวม |

ช่วงงานรวมคีย์ต้นทางและปลายทางด้วย โดยใช้ **ลำดับในไฟล์ต้นฉบับหลักของคลัง** ไม่ใช่ลำดับตัวอักษรหรือลำดับที่เรียงอยู่ในชีต จำกัดไม่เกิน 200 คีย์ สำหรับบทพูด คีย์คือรหัส `file` ในสคริปต์ ไม่เติม `.wav` หรือ `.flac`

หนึ่งใบงานใช้หนึ่งภาษาและหนึ่งตาราง UI หรือหนึ่งบทบาทเสียง ช่วงสั้นจะตรวจได้ง่ายกว่าและลดปัญหาเมื่อข้อความในเกมเปลี่ยน

## 2. จองงานก่อนเริ่มแปล

ผู้ดูแลคอมเมนต์ใน issue ว่า:

```text
/work assign
```

รอบอตยืนยันว่าจองแล้ว การกรอกหรือปิด issue หรือพิมพ์ชื่อในชีตไม่ได้จองหรือคืนงาน

บอตบันทึกงานใน `registry.json` บนสาขา `community-work-state` และตรึงข้อมูลใบงาน คีย์ที่แน่นอน และแฮชต้นฉบับไว้ หากช่วงงานทับกับงานที่ยังใช้งานอยู่ซึ่งมีชนิด ภาษา และตารางหรือบทบาทเดียวกัน บอตจะปฏิเสธ คนละภาษาสามารถทำคีย์ต้นฉบับชุดเดียวกันได้

การแก้เนื้อหา issue ภายหลังไม่เปลี่ยนงานที่จองแล้ว หากต้องเปลี่ยนช่วงงาน เอกสาร ผู้แปล หรือผู้ตรวจ ให้ผู้ดูแลคืนงานและสร้างการจองที่ถูกต้องใหม่

## 3. แปลในชีต

ผู้ดูแลเตรียมแถวต้นฉบับล่าสุดและให้สิทธิ์แก้ไขแก่ผู้รับงาน บอตต้องอ่านเอกสารได้โดยไม่เข้าสู่ระบบ Google แต่สิทธิ์แก้ไขต้องจำกัดเฉพาะผู้ทำงานนั้น ป้องกันคอลัมน์คีย์และภาษาอังกฤษ เปิดให้แก้เฉพาะช่องที่จำเป็น อย่าเปิดให้ทุกคนที่มีลิงก์แก้ไขได้ สิทธิ์และช่วงที่ป้องกันต้องตั้งด้วยมือ บอต GitHub ไม่ได้จัดการสิทธิ์ Google

งานแปล UI ต้องคงสี่คอลัมน์นี้:

```text
key,en,translation,status
```

แท็บต้องมีแถวจากตาราง UI เดียวตามใบงาน รายการรวมหลายตารางใช้เป็นข้อมูลอ้างอิงได้ แต่ไม่ใช่แท็บที่นำเข้าผ่านใบงานได้โดยตรง บอตจะตรวจทุกแถวที่มีข้อมูลในแท็บนั้นกับตารางต้นฉบับที่ระบุ

แก้ `translation` และใช้ค่า `status` ที่มีอยู่ แถว UI พร้อมนำเข้าเฉพาะเมื่อ `status` ว่าง ค่า `review` และ `outdated` จะพักการนำเข้า สถานะว่างไม่ได้แปลว่าอนุมัติแล้ว ยังต้องผ่านผู้ตรวจแยกต่างหาก

งานแปลบทพูดแบบข้อความต้องใช้หัวคอลัมน์และลำดับนี้ตรงทุกตัว:

```text
Take file,English source,Translation,Review status,Notes,Role,Situation,Tone,Current voices,Source readiness,Source file,Source record
```

แท็บภาษาญี่ปุ่น รัสเซีย และเกาหลีที่มีอยู่ใช้รูปแบบนี้ บอตกรองจากค่า `Role` ที่ตรงกัน เช่น `carrier_jet_pilot` แล้วเลือกคีย์ `Take file` ที่จองไว้ กรอก `Translation` และเมื่อข้อความผ่านการตรวจแล้ว ให้ตั้ง `Review status` เป็น `Approved`

ข้อความที่อนุมัติจะถูกเขียนลง `voice/translations/<locale>/<role>.csv` โดยใช้ `key,en,translation,status` นี่เป็นการนำเข้าข้อความบทพูดเท่านั้น ไม่ใช่การอนุมัติเสียงบันทึก และไม่ได้ยืนยันว่าบทพูดร่างนั้นถูกนำไปใช้งานในเกมแล้ว

งานทั้งสองแบบต้องทำตามนี้:

- รักษาตัวแปร แท็กที่จำเป็น และสัญลักษณ์ขึ้นบรรทัดใหม่ให้ครบ
- คีย์และภาษาอังกฤษต้องตรงกับต้นฉบับที่ได้รับมอบหมาย
- แปลให้ครบทุกคีย์ที่จองก่อนขอสำเนาตัวอย่าง
- ใส่ข้อความในเซลล์โดยตรง ไม่ใช้สูตรดึงหรือประกอบคำแปล
- ไม่ใส่ข้อมูลติดต่อส่วนตัว ข้อความจากทิกเก็ต หรือไฟล์ออดิชันในเอกสารงานและ issue

หากงานใหญ่เกินกว่าจะทำให้เสร็จ ให้ตกลงแบ่งงานหรือคืนงานกับผู้ดูแล แทนการจองงานที่ทำค้างไว้โดยไม่มีกำหนด

## 4. ขอและตรวจสำเนาตัวอย่าง

ผู้แปลที่ได้รับมอบหมาย ผู้ตรวจที่ได้รับมอบหมาย หรือผู้ดูแลคอมเมนต์ว่า:

```text
/work preview
```

บอตอ่านช่วงที่จองจาก CSV สาธารณะที่ Google ชีตส่งออก แล้วตรวจต้นฉบับที่ตรึงไว้ สถานะ คำแปลที่ต้องไม่ว่าง และตัวแปรที่จำเป็น บอตยังตรวจคำแปลปัจจุบันในคลัง เพื่อให้ตอนอนุมัติตรวจพบการแก้ของคนอื่นได้

บอตบันทึกสำเนาที่แก้ไขไม่ได้ พร้อมเผยแพร่ลิงก์และค่าแฮช SHA-256 ผู้ตรวจต้องอ่าน **สำเนาฉบับนั้นจริง ๆ** ไม่ใช่แค่สรุป issue หรือชีตปัจจุบัน เพราะชีตอาจเปลี่ยนหลังสร้างตัวอย่าง ตรวจความหมายและบริบท สำนวนและศัพท์ ความยาวบนหน้าจอหรือการออกเสียง ตำแหน่งตัวแปร แท็ก และบรรทัดใหม่

หากต้องแก้ ให้แก้ชีตแล้วเรียก `/work preview` ใหม่ ใช้ค่าแฮชใหม่เสมอ ลิงก์ตัวอย่างเป็นเอกสารให้ตรวจ ไม่ใช่สิทธิ์รวม PR

## 5. อนุมัติสำเนาที่ตรงกัน

เฉพาะผู้ตรวจที่ได้รับมอบหมายเท่านั้นที่คอมเมนต์คำสั่งนี้ โดยแทนข้อความตัวอย่างด้วยแฮชครบ 64 ตัวอักษรจากสำเนา:

```text
/work approve <sha256>
```

คัดลอกอักขระทั้ง 64 ตัวหลัง `Digest:` ในข้อความตอบกลับตัวอย่างของบอต แล้วแทนเฉพาะ `<sha256>` ในคำสั่ง อย่าแปลคำสั่งหรือส่งคำว่า `<sha256>` ตามตัวอย่างโดยไม่แทนค่า

บอตตรวจตัวตนผู้ตรวจและอ่านชีตอีกครั้ง ซึ่งต้องตรงกับสำเนาที่อนุมัติ นอกจากนี้ยังตรวจว่าต้นฉบับและเนื้อหาปลายทางในคลังไม่เปลี่ยนจากตอนสร้างตัวอย่าง หากชีตหรือไฟล์ปลายทางเปลี่ยน ต้องสร้างตัวอย่างใหม่ หากตารางต้นฉบับหลักเปลี่ยน ต้องสร้างใบงานใหม่ตามหัวข้อด้านล่าง

เมื่อผ่าน บอตจะเปิด PR พร้อมไฟล์ที่ตรวจแล้ว แต่ **ไม่รวม PR ให้** ค่า `Approved` ในชีตหรือคอมเมนต์บอกว่าเห็นด้วยธรรมดาใช้แทนคำสั่งนี้ไม่ได้ งานยังถูกจองจนกว่าผู้ดูแลตรวจส่วนต่าง ผ่านการตรวจอัตโนมัติ และรวม PR การพูดคุยเรื่องไฟล์ที่เสนอควรอยู่ใน PR นั้น

กฎที่เชื่อถือได้ชื่อ `reviewed-sheet` เปรียบเทียบ PR กับใบงานที่บันทึกไว้และสำเนาที่อนุมัติ กฎนี้อ่านไฟล์ PR เป็นข้อมูล และรันโค้ดที่เชื่อถือได้จากสาขาหลัก จะปฏิเสธ PR แปลที่สร้างด้วยมือ ไฟล์ส่งงานที่ถูกแก้ หรือไฟล์อื่นที่แถมมากับงานแปล การแก้สาขาของบอตหลังอนุมัติไม่สามารถสลับข้อความที่ตรวจแล้วเป็นข้อความอื่นได้

## 6. ปิดงานหรือคืนการจอง

หลังรวม PR หรือปิด PR ผู้ดูแลเรียก:

```text
/work sync
```

PR ที่รวมแล้วทำให้งานเสร็จ ส่วน PR ที่ปิดโดยไม่รวมจะคืนการจอง ตรวจคำยืนยันจากบอต อย่าสรุปจากสถานะ issue อย่างเดียว ตัวประสานงานจะปรับสถานะเมื่อ GitHub ส่งเหตุการณ์ปิด PR ของบอตที่มีบันทึกไว้ด้วย หากรอบอัตโนมัติไม่เสร็จ ให้ใช้คำสั่งเอง สำหรับ PR ที่ยังเปิดอยู่ `/work sync` จะขอรันการตรวจอีกครั้ง หากตอนสร้าง PR สั่งรันไม่สำเร็จ

หากจะยกเลิกงานก่อนมี PR ผู้ดูแลคอมเมนต์ว่า:

```text
/work release
```

ถ้ามี PR เปิดอยู่ ต้องปิดก่อนคืนงาน เพื่อไม่ให้มีผลงานสองชุดที่กำลังดำเนินการในช่วงเดียวกัน

| คำสั่ง | ผู้ใช้ได้ | ผล |
| --- | --- | --- |
| `/work assign` | ผู้ดูแล | ตรึงใบงานและจองช่วงคีย์ |
| `/work preview` | ผู้แปลที่รับงาน ผู้ตรวจที่รับงาน หรือผู้ดูแล | ตรวจและเก็บสำเนาสำหรับทบทวน |
| `/work approve <sha256>` | ผู้ตรวจที่รับงาน | ตรวจสำเนาฉบับเดิมอีกครั้งแล้วเปิด PR |

## เมื่อต้นฉบับเกมเปลี่ยน

ไม่ต้องสร้างเอกสารใหม่สำหรับเกมทุกเวอร์ชัน ID ที่คงเดิมช่วยรักษาคำแปลไว้ เพิ่มแถวผ่านกระบวนการอัปเดตต้นฉบับในคลัง และทำเครื่องหมายคำแปลที่เปลี่ยนให้ตรวจตาม[คู่มือการแปล](../../localization/README.md)

ใบงานตรึงต้นฉบับของ **ทั้งตาราง UI หรือทั้งบทบาทเสียง** หากตารางหลักนั้นเปลี่ยนก่อนอนุมัติ บอตจะหยุดนำเข้า แม้คีย์ที่จองจะไม่เปลี่ยนก็ตาม ผู้ดูแลต้องปิด PR ส่งงานที่ยังเปิด คืนใบงานเดิม อัปเดตแถวต้นฉบับในชีต และเปิด **issue ใบงานใหม่** เก็บคำแปลของอาสาสมัครไว้แล้วเทียบกับต้นฉบับใหม่ จากนั้นผู้ตรวจจึงตรวจสำเนาตัวอย่างใหม่ งานของตารางต้นฉบับอื่นยังทำต่อได้

แถวแผนงานที่ไม่มี ID ต้นฉบับจริงยังนำเข้าระบบนี้ไม่ได้ ให้คงไว้ในส่วนวางแผนจนผู้พัฒนาเพิ่มข้อมูลหลัก อย่าสร้าง ID ใช้งานจริงขึ้นเอง หรืออัปโหลดทั้งเอกสารเพียงเพื่อรวมเนื้อหาในอนาคต

## การตั้งค่าและข้อจำกัดสำหรับผู้ดูแล

- เปิดระบบเมื่อโค้ดและแบบฟอร์ม issue รวมอยู่ในสาขาหลักแล้วเท่านั้น อย่าแก้ทะเบียน `community-work-state` ด้วยมือระหว่างที่คำสั่งกำลังทำงาน
- ระบบใช้ `GITHUB_TOKEN` ของคลัง พร้อมสิทธิ์เขียนสถานะและสาขาบอต คอมเมนต์ issue และสร้าง PR ไม่ต้องเชื่อม Google OAuth หรือใช้โทเคนส่วนตัว การเข้าถึง Google มีแค่การอ่าน CSV สาธารณะ
- ในการตั้งค่า Actions อนุญาตให้ GitHub Actions สร้าง PR แยกตัวตนบอตออกจากบัญชีผู้ตรวจภาษาที่เป็นคน
- อย่าอาศัยว่า PR ของบอตจะเรียก workflow `pull_request` ทั่วไปเอง ตัวนำเข้าตรวจไฟล์ก่อนสร้าง PR แล้วสั่ง `check.yml` สำหรับสาขาบอตและ `delivery-policy.yml` จากสาขาหลักที่เชื่อถือได้สำหรับหมายเลข PR นั้นโดยตรง
- ป้องกันสาขาหลักด้วยการตรวจที่บังคับทั้ง `check` และสถานะ commit `reviewed-sheet` workflow ของกฎต้องเผยแพร่สถานะนี้ได้ ตรวจให้แน่ใจว่าทั้งสองผ่านก่อนรวม PR การเพิ่มไฟล์ workflow อย่างเดียวไม่ได้เปิดกฎป้องกันสาขา
- ทะเบียนป้องกันการรับงานซ้อน ส่วนกฎส่งงานที่บังคับป้องกันการข้ามด้วย PR แปลที่เปิดเอง ทั้งคู่ไม่ได้จัดการสิทธิ์ Google ชีต จึงต้องจำกัดการแก้และป้องกันคอลัมน์ต้นฉบับเอง

การตรวจอัตโนมัติช่วยจับโครงสร้างผิดและเนื้อหาที่ล้าสมัย ส่วนคุณภาพภาษา บริบท เงื่อนไขการร่วมงาน และความเหมาะสมกับเกมยังต้องให้คนตรวจ
