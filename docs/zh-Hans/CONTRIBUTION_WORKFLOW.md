# 翻译任务单

> **录音提交：** 请参阅[私密 Drive 录音提交指南（英语）](../VOICE_SUBMISSIONS.md)。上传并勾选后，由另一位审核者试听并批准，再生成仅包含提交清单的 PR。音频保存在 Drive 中。下文说明台词和 UI 文本的翻译流程。

Google 表格用于填写和审阅译文。GitHub 任务单用于预留工作范围、记录负责人，并控制已审核的译文何时生成拉取请求（PR）。

**修改表格不会自动更新仓库或游戏。** 机器人会将经过审核的特定快照导入 PR。维护者仍需审查并合并该 PR，再由开发者将译文纳入游戏构建版本。

本流程适用于已有 UI 文本和配音台词的文字翻译。录音、试音、新台词草稿，以及尚无源文本 ID 的内容，需按各自的准备流程处理。

社区翻译必须通过任务单机器人创建交付 PR。手动创建翻译 PR 不能绕过任务预留和快照审核。

本文以[英文指南](../CONTRIBUTION_WORKFLOW.md)为参考。欢迎母语使用者反馈不自然或不清楚的表述。

阅读指南或列入报名名单，不等于已预留任务或已批准提交。请以机器人的预留确认为准。

请将命令作为评论发到已分配的 GitHub 任务单议题中。批准时，从机器人的预览回复中复制 `Digest:` 后的全部 64 个字符，只替换示例中的 `<sha256>`。命令保持英文，不要直接发送占位符 `<sha256>`。

## 角色与职责

| 角色 | 职责 |
| --- | --- |
| 贡献者 | 在表格中完成分配给自己的翻译，并请求生成预览。 |
| 审阅者 | 检查语境、术语、措辞是否自然，以及预览中的具体内容，并用自己的 GitHub 账号批准该快照的摘要值。 |
| 维护者 | 创建或核对任务单、预留工作范围、管理表格权限、审查生成的 PR，并将其合并。 |

贡献者和审阅者必须是不同的 GitHub 用户。机器人只核验身份和文件结构，不会判断译文是否自然。

贡献者可以全程在 Google 表格中完成翻译，无需安装 Git、克隆仓库或自行创建 PR。批准预览的人需要 GitHub 账号。如果贡献者不熟悉 GitHub 评论，维护者可以代为请求预览。

## 1. 先商定一个小任务

通过现有的译者申请议题或 Discord 支持工单报名。开始前，由维护者与参与者确定语言、贡献者、审阅者和工作范围。

私有报名表只用于整理申请，不是任务预留登记表。其中的内容不应复制到公开的 GitHub 议题中。

创建一个 [**Translation work order** 议题](https://github.com/Epheria/Ebbtide-Community/issues/new?template=work_order.yml)，填写以下字段。表单字段名称保持英文：

| 字段 | 填写内容 |
| --- | --- |
| Kind | `ui` 或 `voice-text`。 |
| Locale | 仓库使用的语言代码，例如 `ja`、`ru` 或 `pt-BR`。 |
| Table or voice role | 已有源文本表或配音角色的名称，不含路径或 `.csv` 扩展名。 |
| Contributor | 一位贡献者的 GitHub 用户名，不含 `@`。 |
| Reviewer | 另一位用户的 GitHub 用户名，不含 `@`。 |
| Spreadsheet URL | 本任务使用的 Google 表格文件网址。 |
| Sheet tab | 工作表标签页的完整名称，必须完全一致。 |
| First key | 工作范围内第一个已有源文本键。 |
| Last key | 工作范围内最后一个已有源文本键。 |

工作范围按**仓库标准源文件中的顺序**确定，包含首尾两个键，不按字母顺序或表格当前行序确定。每单最多包含 200 个键。对于配音台词，键为脚本中的 `file` 标识符，不含 `.wav` 或 `.flac`。

每张任务单只对应一种语言，以及一张 UI 表或一个配音角色。范围较小更便于审阅，也能减少游戏文本变动时的冲突。

## 2. 预留成功后再开始翻译

维护者在议题中评论：

```text
/work assign
```

等待机器人确认预留成功。填写议题、关闭议题或在表格中填入姓名，都不会预留或释放任务。

机器人将分配记录写入 `community-work-state` 分支的 `registry.json`，并固定议题字段、具体源文本键和源文件哈希值。如果同一类型、语言、UI 表或配音角色已有其他进行中的任务占用了相同范围，机器人会拒绝重叠分配。不同语言可以同时翻译相同的源文本键。

之后修改议题正文，不会改变已有分配。若需更改范围、表格文件、贡献者或审阅者，请维护者释放旧任务，再创建更正后的预留。

## 3. 在表格中填写译文

维护者提供当前源文本行，并授予相关人员编辑权限。机器人必须能够在不登录 Google 的情况下读取表格，但编辑权限应只授予本任务的参与者。

保护源文本键和英文原文列，只允许贡献者编辑所需的输入单元格。不要启用“知道链接的任何人都可以编辑”。表格权限和受保护范围需要手动设置；GitHub 机器人不会管理 Google 权限。

UI 翻译须保留以下四个 CSV 列名：

```text
key,en,translation,status
```

该标签页只能包含任务单中指定的那张 UI 表的行。汇总多张表的总表可以用作参考，不能直接作为任务单的导入标签页。机器人会将所选标签页中所有已填充的行与指定源文本表核对。

填写 `translation`，并沿用现有的 `status` 值。UI 行只有在 `status` 留空时才可导入。标为 `review` 或 `outdated` 的行会被暂缓处理。状态留空本身不代表批准，仍需完成下方独立的审核步骤。

配音台词的文字翻译须按此顺序保留以下列名，不能更改：

```text
Take file,English source,Translation,Review status,Notes,Role,Situation,Tone,Current voices,Source readiness,Source file,Source record
```

现有日语、俄语和韩语配音标签页采用此格式。机器人先按 `Role` 的精确值筛选，例如 `carrier_jet_pilot`，再选取已预留的 `Take file` 键。填写 `Translation`，并将审阅通过的行在 `Review status` 中标为 `Approved`。

通过审核的文字会以 `key,en,translation,status` 格式写入 `voice/translations/<locale>/<role>.csv`。此操作只导入台词文字，不代表录音已获批准，也不代表某句草稿台词已在游戏中实现。

两类任务均须遵守以下要求：

- 保留占位符、必需标签和换行标记。
- 保持源文本键和英文原文与所分配的源文本完全一致。
- 预览前，完成预留范围内的每一条翻译。
- 将表格单元格作为文本使用，不要用公式获取或拼接译文。
- 不要将私人联系方式、工单消息或试音文件放入任务表格或公开议题。

如果任务范围过大、无法完成，请与维护者拆分或释放任务，不要让未完成的预留长期闲置。

## 4. 请求并审阅预览

已分配的贡献者、审阅者或维护者在议题中评论：

```text
/work preview
```

机器人通过 Google 表格公开的 CSV 导出读取预留范围，检查固定的源文本、状态、译文是否为空，以及必需变量。它还会记录仓库中当前的译文，以便在之后批准时识别其他人是否改动过目标内容。

机器人保存不可修改的快照，并发布其 SHA-256 摘要值及审阅链接。请审阅快照本身，不要只看议题摘要或实时表格。快照才是拟提交的内容；生成预览后，实时表格仍可能发生变化。

审阅者需检查：

- 含义和语境是否与英文原文一致。
- 措辞是否自然，术语是否与词汇表一致。
- 相关 UI 的文字长度或台词念出的效果。
- 占位符的位置、标签和换行。

如需修改，请更新表格，再运行一次 `/work preview`，并使用新的摘要值。预览链接只是待审阅的材料，不代表获准合并。

## 5. 批准指定快照

只有已分配的审阅者可以评论以下命令，并将示例替换为预览中完整的摘要值：

```text
/work approve <sha256>
```

机器人核验审阅者身份，再次读取表格，并要求其内容与获批快照一致。它也会检查源文本和仓库目标内容在预览后是否发生变化。表格或目标文件有变动时，需要重新预览。标准源文本表发生变化时，则需重新分配任务，详见下文。

检查成功后，机器人使用已验证的文件创建 PR，**不会自动合并**。表格中的 `Approved`，或普通的“没问题”评论，都不能代替该命令。

维护者审查差异，并在检查通过后合并 PR。在此之前，任务仍保持预留。关于拟提交文件的讨论应集中在该 PR 中，方便追踪最终修改。

受信任的 `reviewed-sheet` 策略会对照任务单记录和获批快照检查 PR。它将 PR 文件作为数据读取，运行的是受信任的默认分支代码。手动创建的翻译 PR、被改动的交付文件，或混入额外文件的获批交付，都会被拒绝。批准后修改机器人分支，不能将已审阅快照替换为其他文本。

## 6. 完成或释放预留

PR 合并或关闭后，运行：

```text
/work sync
```

该命令同步登记状态：已合并的 PR 会使任务完成；已关闭但未合并的 PR 会释放任务。请查看机器人的确认，不要认为议题状态变化就等于预留状态已改变。

GitHub 发出 PR 关闭事件时，协调工作流也会同步已登记的机器人 PR。如果自动同步未完成，可用 `/work sync` 手动处理。对于仍打开的 PR，`/work sync` 还会重新请求运行检查；若 PR 创建后的检查派发失败，可使用此命令。

若尚未创建 PR，维护者可评论以下命令取消分配：

```text
/work release
```

若已有打开的 PR，必须先关闭，再释放任务。这样可以避免同一预留范围出现两份同时有效的提交。

## 命令速查

| 命令 | 可运行者 | 结果 |
| --- | --- | --- |
| `/work assign` | 维护者 | 固定任务单内容，并预留源文本范围。 |
| `/work preview` | 已分配的贡献者、审阅者或维护者 | 验证并保存供审阅的快照。 |
| `/work approve <sha256>` | 已分配的审阅者 | 再次核对指定快照，并创建 PR。 |
| `/work release` | 维护者 | 在没有打开的 PR 时取消预留。 |
| `/work sync` | 维护者 | 将已合并或关闭的 PR 状态同步至登记表。 |

## 游戏文本变动时

无需为每个游戏版本创建新表格。稳定的源文本 ID 能让已有译文在常规更新后继续保留。请通过仓库的源文本更新流程添加新行，并按[本地化说明](../../localization/README.md)将原文已变更的译文标为待复审。

分配任务时，固定的是其所在整张 UI 表或整个配音角色的源文本快照。如果批准前，该标准源文本表发生任何变化，即使预留键本身没有改变，机器人也会停止导入。维护者须关闭任何已打开的交付 PR、释放旧任务单、更新表格的源文本行，再创建一张**新的任务单议题**。保留志愿者已完成的译文，并对照更新后的源文本检查，再由审阅者审阅新的预览。其他源文本表的任务可以继续。

没有真实源文本 ID 的规划行尚不能导入。请先留在规划区，等开发者添加正式源文本条目。不要自行编造正式 ID，也不要只为了夹带未来内容而上传整张表格。

## 维护者配置与限制

任务单代码和议题表单合并至默认分支后，才能启用此工作流。状态登记表保存在 `community-work-state` 分支；命令执行期间不要手动修改。

工作流使用仓库的 `GITHUB_TOKEN`，并需要相应仓库权限，以写入状态及机器人分支、在议题中评论和创建 PR。它不需要 Google OAuth 连接或个人访问令牌。Google 访问仅限读取公开的 CSV 导出。

在仓库的 Actions 设置中，允许 GitHub Actions 创建 PR。机器人的身份必须与人工语言审阅者分开。

不要假设机器人创建的 PR 会自动触发普通的 `pull_request` 工作流。导入器在创建 PR 前会验证候选文件，并明确派发机器人分支上的 `check.yml`，以及受信任默认分支上的 `delivery-policy.yml`，后者使用该 PR 编号。

保护默认分支，并将 `check` 和 `reviewed-sheet` 提交状态均设为必需检查。策略工作流必须有权限发布该状态。合并前确认两项检查均成功；仅添加工作流文件，不会自动配置仓库的分支保护。

任务登记表防止重复分配；必需的交付策略防止手动翻译 PR 绕过分配流程。两者都不会管理 Google 表格的编辑权限。请限制编辑权限，并保护源文本列。

自动检查负责发现结构问题和过期内容。翻译质量、语境、贡献者条款及是否适合游戏，仍由人工审阅负责。
