# 翻訳の作業依頼と進め方

> **録音の提出：** [非公開 Drive への録音提出ガイド（英語）](../VOICE_SUBMISSIONS.md)をご覧ください。アップロードとチェックの後、別の担当者が聴いて承認し、提出一覧のみの PR を作成します。音声は Drive に保管します。以下は台本・UI の翻訳手順です。

英語の[原文](../CONTRIBUTION_WORKFLOW.md)を基準にしています。日本語の言い回しについても、ご意見をお寄せください。

Google スプレッドシートで翻訳と確認を行い、GitHub の作業依頼 Issue で担当範囲と担当者を確定します。承認された内容は、ボットがプルリクエストとして提出します。

**シートを書き換えただけでは、リポジトリにもゲームにも反映されません。** ボットが取り込むのは、確認担当者が承認した時点の内容です。そのプルリクエストをメンテナーが確認してマージし、開発者がゲームのビルドに取り込みます。

シートの案内や応募者一覧への記載だけでは、作業の予約や提出の承認にはなりません。

対象は、既存の UI テキストと音声台本の**文章の翻訳**です。録音、オーディション、新しいセリフの草案、原文 ID がまだない文章は、別の準備工程で扱います。UI・台本翻訳の提出用プルリクエストは作業依頼ボットで作成してください。手動で作成しても、担当範囲の予約とスナップショットの承認は省略できません。

コマンドは、割り当てられた GitHub の作業依頼 Issue にコメントとして投稿します。承認するときは、ボットのプレビュー返信の `Digest:` に続く 64 文字をすべてコピーし、例の `<sha256>` の部分だけを置き換えてください。コマンドは英語のまま使い、`<sha256>` をそのまま投稿しないでください。

## 役割

| 担当 | 行うこと |
| --- | --- |
| 翻訳担当者 | 割り当てられた範囲をシートで翻訳し、プレビューを依頼します。 |
| 確認担当者 | 文脈、用語、自然な表現、プレビューの実際の内容を確認し、自分の GitHub アカウントでそのダイジェストを承認します。 |
| メンテナー | 作業依頼の作成・確認、範囲の予約、シートの権限管理、提出されたプルリクエストの確認とマージを行います。 |

翻訳担当者と確認担当者には、**別々の GitHub ユーザー**を指定します。ボットはユーザーとファイル形式を確認しますが、訳文が自然かどうかは判断しません。

翻訳作業そのものは Google スプレッドシートで完結します。Git のインストール、リポジトリのクローン、自分でのプルリクエスト作成は不要です。プレビューの承認には、確認担当者本人の GitHub アカウントが必要です。GitHub のコメント操作が難しい場合は、メンテナーが翻訳担当者に代わってプレビューを依頼できます。

## 1. 小さな作業範囲を相談する

既存の翻訳者応募 Issue、または Discord のサポートチケットから応募してください。作業を始める前に、メンテナーと対象言語、翻訳担当者、確認担当者、範囲を決めます。

非公開の応募者シートは受付用です。予約台帳ではありません。連絡先やチケットの内容を、公開の GitHub Issue に転記しないでください。

[Translation work order の Issue](https://github.com/Epheria/Ebbtide-Community/issues/new?template=work_order.yml)を開き、次の項目を記入します。フォーム上の英語の項目名は、以下のとおりです。

| 項目 | 記入する内容 |
| --- | --- |
| Kind | `ui` または `voice-text` |
| Locale | `ja`、`ru`、`pt-BR` など、リポジトリで使う言語コード |
| Table or voice role | 既存の原文テーブル名または役名。パスや `.csv` は付けません。 |
| Contributor | 翻訳担当者 1 人の GitHub ログイン名。`@` は付けません。 |
| Reviewer | 別の確認担当者の GitHub ログイン名。`@` は付けません。 |
| Spreadsheet URL | この作業に使う Google スプレッドシートの URL |
| Sheet tab | シートのタブ名と完全に同じ名前 |
| First key | 範囲に含める最初の既存の原文キー |
| Last key | 範囲に含める最後の既存の原文キー |

範囲は、**正式な原文ファイルの並び順で、両端のキーを含めて**指定します。五十音順・アルファベット順や、現在のシート上の行順ではありません。1 件につき最大 200 キーです。音声台本では、台本の `file` 識別子がキーになります。`.wav` や `.flac` は付けません。

1 件の依頼は、1 言語と、1 つの UI テーブルまたは 1 つの役に限定してください。小さく区切ると確認しやすく、開発中の原文変更による競合も減らせます。

## 2. 翻訳を始める前に予約する

メンテナーが Issue に次のコメントを投稿します。

```text
/work assign
```

**ボットが予約を確認するまで待ってください。** Issue の記入やクローズ、シートへの名前の記入だけでは、作業は予約も解除もされません。

予約は `community-work-state` ブランチの `registry.json` に記録されます。Issue の項目、対象の原文キー、原文のハッシュが固定されます。同じ種類・言語・テーブルまたは役で、ほかの有効な依頼とキーが重なる予約は拒否されます。別の言語なら、同じ原文キーに取り組めます。

あとから Issue 本文を編集しても、有効な予約は変わりません。範囲、使用するブック、翻訳担当者、確認担当者を変える場合は、メンテナーに解除と新しい依頼の作成をお願いしてください。

## 3. シートで翻訳する

メンテナーが現在の原文を用意し、担当者に編集権限を渡します。ブックはボットが Google にログインせずに読める状態にし、編集できる人は担当者に限定します。

原文キーと英語の列は保護し、翻訳担当者には必要な入力セルだけを編集可能にしてください。「リンクを知っている全員が編集可」にはしません。権限と保護範囲は手動で設定します。GitHub ボットは Google の権限を管理しません。

UI 翻訳では、次の 4 列をこのまま使います。

```text
key,en,translation,status
```

作業依頼に指定した **1 つの UI テーブルだけ**を含むタブを使ってください。複数のテーブルをまとめた一覧は参照用で、そのまま取り込める作業用タブではありません。ボットは選んだタブの入力済みの全行を、そのテーブルの原文と照合します。

`translation` を入力し、`status` は既存の値を使います。UI の取り込み対象になるのは、`status` が空欄の行だけです。`review` と `outdated` の行は保留されます。空欄にしただけでは承認にならず、後述の確認・承認が必要です。

音声台本の文章を翻訳する場合は、次の見出しと順番を維持します。

```text
Take file,English source,Translation,Review status,Notes,Role,Situation,Tone,Current voices,Source readiness,Source file,Source record
```

既存の日本語・ロシア語・韓国語の音声タブはこの形式です。ボットは `carrier_jet_pilot` などの `Role` の値を完全一致で絞り込み、予約した `Take file` のキーを選びます。`Translation` を入力し、確認済みの行の `Review status` を `Approved` にします。

承認した文章は、`key,en,translation,status` の形式で `voice/translations/<locale>/<role>.csv` に保存されます。対象は文章だけです。録音の採用や、草案のセリフがゲームに実装済みであることを意味しません。

どちらの種類でも、以下を守ってください。

- プレースホルダー、必要なタグ、改行トークンを維持します。
- キーと英語は、割り当てられた原文と完全に同じにします。
- 予約範囲の訳文をすべて入力してからプレビューを依頼します。
- セルは文字列として扱います。数式で訳文を取得・生成しないでください。
- 個人の連絡先、非公開チケットの文章、オーディション音声を作業用ブックや Issue に入れないでください。

終えられないほど大きい作業は、メンテナーと相談して分割または解除してください。途中のまま無期限に予約を残さないようにします。

## 4. プレビューを依頼して確認する

割り当てられた翻訳担当者、確認担当者、またはメンテナーがコメントします。

```text
/work preview
```

ボットは公開 CSV 出力から予約範囲を読み、固定した原文、状態、空でない訳文、必要な変数を検査します。ほかの人による変更を承認時に検知できるよう、リポジトリの現在の翻訳ファイルも確認します。

ボットは変更されないスナップショットを保存し、その SHA-256 ダイジェストと確認用リンクを投稿します。Issue の要約や、その後も編集できるシートだけを見るのではなく、**スナップショットの実際の内容**を確認してください。これが提出予定の文章です。

確認担当者は、原文に対する意味と文脈、自然な表現と用語の統一、UI の長さや発話のしやすさ、プレースホルダー・タグ・改行の位置を確認します。

修正が必要ならシートを直し、もう一度 `/work preview` を実行して新しいダイジェストを使います。プレビューのリンクは確認用資料であり、マージの許可ではありません。

## 5. そのスナップショットを承認する

**割り当てられた確認担当者だけ**が、プレビューの完全なダイジェストに置き換えてコメントします。

```text
/work approve <sha256>
```

ボットは確認担当者を照合し、シートを再取得してスナップショットとの一致を確認します。原文と保存先のリポジトリ内容が、プレビュー後に変わっていないことも確認します。シートや保存先ファイルが変わった場合は、新しいプレビューが必要です。正式な原文テーブルが変わった場合は、後述の手順で依頼を作り直します。

成功するとボットがプルリクエストを開きますが、**マージはしません**。シートの `Approved` や、普通の「問題ありません」というコメントでは、このコマンドの代わりになりません。

メンテナーが差分を確認し、チェックの成功後にマージします。それまでは予約が続きます。提出ファイルについての相談は、そのプルリクエストにまとめてください。

信頼された `reviewed-sheet` ポリシーは、記録された依頼と承認済みスナップショットを PR と照合します。PR のファイルをデータとして読み、実行するのはデフォルトブランチのコードだけです。手動の翻訳 PR、承認内容と異なるファイル、余分なファイルを含む提出は拒否します。承認後にボットのブランチを編集しても、確認済みの文章と差し替えることはできません。

## 6. 完了または解除する

プルリクエストのマージまたはクローズ後、メンテナーが実行します。

```text
/work sync
```

マージ済みなら作業を完了し、未マージでクローズされていれば予約を解除します。Issue の状態だけで判断せず、ボットの確認を見てください。

登録されたボット PR は、GitHub のクローズイベントでも自動的に同期します。自動処理が終わらなかった場合は `/work sync` を使ってください。開いている PR では、チェックの再実行も依頼します。PR 作成後にチェックの起動が失敗したときにも使えます。

PR 作成前に依頼を取り消す場合は、メンテナーがコメントします。

```text
/work release
```

開いている PR は、先にクローズしないと解除できません。同じ範囲に有効な提出が 2 件できるのを防ぐためです。

## コマンド一覧

| コマンド | 実行できる人 | 結果 |
| --- | --- | --- |
| `/work assign` | メンテナー | 依頼内容を固定し、原文の範囲を予約します。 |
| `/work preview` | 担当の翻訳者・確認者、メンテナー | 検査し、確認用のスナップショットを保存します。 |
| `/work approve <sha256>` | 担当の確認者 | そのスナップショットを再確認して PR を開きます。 |
| `/work release` | メンテナー | 開いている PR がない予約を取り消します。 |
| `/work sync` | メンテナー | PR の状態を予約台帳と同期します。 |

## ゲームの原文が変わったら

バージョンが変わるたびにブックを作り直す必要はありません。安定した原文 ID を使うことで、通常の更新でも既存の翻訳を引き継げます。新しい行の追加と変更行の確認は、[ローカライズの手順](../../localization/README.md)に従ってください。

予約では、対象の UI テーブルまたは役の**全体**の原文を固定します。承認前にその正式なテーブルが変わると、予約したキー自体が同じでも取り込みは停止します。メンテナーは開いている提出 PR を閉じ、古い予約を解除し、シートの原文を更新して、**新しい作業依頼 Issue** を作成してください。協力者の訳文は残し、新しい原文と照合して、新しいプレビューを確認してもらいます。別テーブルの作業は継続できます。

実在する原文 ID がまだない計画行は、取り込み対象にできません。開発者が正式な原文を追加するまでは計画用の場所に置いてください。将来の内容を入れるために、実運用の ID を独自に作ったり、シート全体を提出したりしないでください。

## メンテナー向けの設定と制限

- ワークフローのコードと Issue フォームをデフォルトブランチにマージしてから有効にします。台帳は `community-work-state` にあります。コマンドの処理中に手動編集しないでください。
- リポジトリの `GITHUB_TOKEN` を使い、台帳・ボットブランチの書き込み、Issue へのコメント、PR 作成に必要な権限を与えます。Google OAuth 接続や個人アクセストークンは不要です。Google へのアクセスは公開 CSV の読み取りだけです。
- Actions の設定で、GitHub Actions による PR 作成を許可してください。ボットと、人間の言語確認担当者は別の主体として扱います。
- ボットが作った PR で通常の `pull_request` ワークフローが起動するとは限りません。取り込み前に候補ファイルを検査し、ボットブランチの `check.yml` と、信頼されたデフォルトブランチの `delivery-policy.yml` を、その PR 番号で明示的に起動します。
- デフォルトブランチでは、`check` とコミット状態 `reviewed-sheet` の両方を必須にしてください。ポリシーのワークフローには、その状態を投稿する権限が必要です。マージ前に両方の成功を確認します。ワークフローファイルを置くだけでは、ブランチ保護は設定されません。
- 台帳は予約の重複を防ぎ、必須の提出ポリシーは手動 PR による迂回を防ぎます。Google シートの編集権限は管理しないので、編集者の制限と原文列の保護は別途設定してください。

自動検査の担当は、構造上の不備と古い内容の検出です。訳文の品質、文脈、協力者向け規約、ゲームにふさわしい内容かどうかは、人が確認します。
