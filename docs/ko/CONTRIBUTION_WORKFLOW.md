# 번역 작업 배정과 제출 절차

> **녹음 파일 제출:** [비공개 Drive 녹음 안내](VOICE_SUBMISSIONS.md)를 따라 주세요. 업로드·체크 후 별도 청취 검수를 거쳐 제출 목록만 PR로 만듭니다. 음성 파일은 Drive에 보관하며, 아래 내용은 대본·UI 번역 절차입니다.

기준 문서는 [영어 원문](../CONTRIBUTION_WORKFLOW.md)입니다. 한국어 표현을 더 자연스럽게 다듬을 의견도 환영합니다.

Google 시트에서 번역하고 검수하며, GitHub 작업 이슈에서 담당 범위와 담당자를 확정합니다. 검수자가 승인한 내용은 봇이 풀 리퀘스트(PR)로 제출합니다.

**시트를 수정한다고 저장소나 게임에 바로 반영되지는 않습니다.** 봇은 검수자가 확인한 내용 그대로를 PR로 옮깁니다. 이후 관리자가 PR을 검토하고 병합하며, 개발자가 게임 빌드에 반영합니다.

시트 안내나 지원자 목록에 이름이 있다고 작업이 예약되거나 제출물이 승인된 것은 아닙니다.

이 절차는 기존 UI 문자열과 **음성 대본의 글 번역**에 적용됩니다. 녹음 파일, 오디션, 새 대사 초안, 아직 원문 ID가 없는 문장은 별도로 준비합니다. UI·대본 번역의 제출 PR은 작업 배정 봇으로 만듭니다. 직접 PR을 열어도 배정과 스냅샷 승인 절차를 건너뛸 수 없습니다.

명령은 배정된 GitHub 작업 이슈에 댓글로 남깁니다. 승인할 때는 봇의 미리보기 답글에서 `Digest:` 뒤의 64글자를 모두 복사해 예시의 `<sha256>` 부분만 바꾸세요. 명령어는 영어 그대로 쓰며 `<sha256>` 자체를 붙여 넣지 않습니다.

## 역할별로 하는 일

| 역할 | 담당하는 일 |
| --- | --- |
| 작업자 | 배정받은 시트 범위를 번역하고 미리보기를 요청합니다. |
| 검수자 | 문맥, 용어, 자연스러운 표현과 실제 미리보기 내용을 확인하고, 본인 GitHub 계정으로 그 해시를 승인합니다. |
| 관리자 | 작업 이슈를 작성하거나 확인하고, 범위를 예약하고, 시트 권한을 관리하며, 생성된 PR을 검토하고 병합합니다. |

작업자와 검수자는 **서로 다른 GitHub 사용자**여야 합니다. 봇은 계정과 파일 구조를 확인할 뿐, 번역이 자연스러운지는 판단하지 않습니다.

번역 작업 자체는 Google 시트에서 모두 할 수 있습니다. Git 설치, 저장소 복제, 직접 PR 만들기는 필요하지 않습니다. 미리보기를 승인하는 검수자는 본인 GitHub 계정이 필요합니다. 작업자가 GitHub 댓글 사용에 어려움을 겪으면 관리자가 대신 미리보기를 요청할 수 있습니다.

## 1. 작은 작업 범위를 정하기

기존 번역자 지원 이슈나 Discord 지원 티켓으로 신청하세요. 작업을 시작하기 전에 관리자와 언어, 작업자, 검수자, 범위를 정합니다.

비공개 지원자 시트는 접수 대기열입니다. 작업 예약 장부가 아닙니다. 연락처나 티켓 내용을 공개 GitHub 이슈로 옮기지 마세요.

[Translation work order 이슈](https://github.com/Epheria/Ebbtide-Community/issues/new?template=work_order.yml)를 열어 아래 항목을 작성합니다. 양식의 영어 항목명은 그대로 표시했습니다.

| 항목 | 작성할 내용 |
| --- | --- |
| Kind | `ui` 또는 `voice-text` |
| Locale | `ko`, `ja`, `ru`, `pt-BR` 같은 저장소 언어 코드 |
| Table or voice role | 기존 원문 테이블명 또는 배역명. 경로나 `.csv` 확장자는 제외합니다. |
| Contributor | 작업자 한 명의 GitHub 로그인명. `@`는 제외합니다. |
| Reviewer | 작업자와 다른 검수자의 GitHub 로그인명. `@`는 제외합니다. |
| Spreadsheet URL | 이 작업에서 사용할 Google 시트 문서 주소 |
| Sheet tab | 실제 워크시트 탭과 정확히 같은 이름 |
| First key | 범위에 포함할 첫 번째 기존 원문 키 |
| Last key | 범위에 포함할 마지막 기존 원문 키 |

범위는 **정식 원문 파일의 순서에 따라 양 끝 키를 모두 포함**합니다. 가나다순·알파벳순이나 현재 시트의 정렬 순서가 아닙니다. 한 작업에 최대 200개 키까지 배정할 수 있습니다. 음성 대본은 `file` 식별자가 키이며, `.wav`나 `.flac`은 붙이지 않습니다.

작업 하나는 한 언어와 UI 테이블 하나 또는 배역 하나로 제한합니다. 짧게 나누면 검수하기 쉽고 개발 중 원문이 바뀔 때 충돌도 줄어듭니다.

## 2. 번역하기 전에 범위 예약하기

관리자가 이슈에 댓글을 답니다.

```text
/work assign
```

**봇의 예약 확인을 기다린 뒤 시작하세요.** 이슈를 작성하거나 닫는 것, 시트에 이름을 쓰는 것만으로는 예약되거나 해제되지 않습니다.

봇은 `community-work-state` 브랜치의 `registry.json`에 배정 내용을 기록합니다. 이슈 항목, 정확한 원문 키, 원문 해시가 고정됩니다. 종류·언어·테이블 또는 배역이 같고 키가 겹치는 활성 배정은 거절합니다. 언어가 다르면 같은 원문 키를 번역할 수 있습니다.

이후 이슈 본문을 수정해도 기존 배정은 바뀌지 않습니다. 범위, 작업 문서, 작업자, 검수자를 바꿔야 한다면 관리자에게 예약 해제와 새 작업 이슈 생성을 요청하세요.

## 3. 시트에서 번역하기

관리자가 최신 원문 행을 준비하고 담당자에게 편집 권한을 줍니다. 문서는 봇이 Google 로그인 없이 읽을 수 있어야 하지만, 편집 권한은 작업하는 사람으로 제한해야 합니다.

원문 키와 영어 열을 보호하고 작업자에게 필요한 입력 셀만 열어 주세요. ‘링크가 있는 모든 사용자에게 편집 허용’으로 설정하지 마세요. 공유 권한과 보호 범위는 직접 설정해야 합니다. GitHub 봇은 Google 권한을 관리하지 않습니다.

UI 번역은 다음 네 열을 유지합니다.

```text
key,en,translation,status
```

작업 이슈에 지정한 **UI 테이블 하나의 행만 들어 있는 탭**을 사용하세요. 여러 테이블을 합친 전체 목록은 참고용이며, 그대로 가져올 수 있는 작업 탭이 아닙니다. 봇은 선택한 탭의 값이 있는 모든 행을 해당 원문 테이블과 대조합니다.

`translation`을 입력하고 `status`는 기존 값만 사용합니다. UI 행은 `status`가 비어 있어야 가져올 수 있습니다. `review`나 `outdated` 행은 보류합니다. 빈 상태만으로 승인되는 것은 아니며, 아래의 별도 검수와 승인 과정이 필요합니다.

음성 대본의 글 번역은 아래 제목과 순서를 그대로 유지합니다.

```text
Take file,English source,Translation,Review status,Notes,Role,Situation,Tone,Current voices,Source readiness,Source file,Source record
```

기존 일본어·러시아어·한국어 음성 탭은 이 형식을 사용합니다. 봇은 `carrier_jet_pilot`처럼 `Role` 값이 정확히 일치하는 행을 추린 뒤 예약된 `Take file` 키를 선택합니다. `Translation`을 입력하고 검수한 행의 `Review status`를 `Approved`로 표시합니다.

승인된 글은 `key,en,translation,status` 형식으로 `voice/translations/<locale>/<role>.csv`에 저장됩니다. 이는 **글만 가져오는 과정**입니다. 녹음을 승인하거나 대사 초안이 게임에 구현되어 있다고 확인하는 과정이 아닙니다.

두 종류 모두 아래를 지켜 주세요.

- 플레이스홀더, 필요한 태그, 줄바꿈 토큰을 유지합니다.
- 키와 영어는 배정된 원문과 정확히 같아야 합니다.
- 예약 범위의 번역을 모두 채운 뒤 미리보기를 요청합니다.
- 셀은 텍스트로 취급합니다. 수식으로 번역을 가져오거나 만들지 마세요.
- 개인 연락처, 비공개 티켓 내용, 오디션 파일은 작업용 문서와 이슈에 넣지 마세요.

끝내기 어려울 만큼 큰 작업은 관리자와 나누거나 해제하세요. 일부만 작업한 채로 무기한 예약을 유지하지 않도록 합니다.

## 4. 미리보기 요청하고 검수하기

배정된 작업자, 검수자 또는 관리자가 댓글을 답니다.

```text
/work preview
```

봇은 공개 Google 시트 CSV에서 예약 범위를 읽고, 고정된 원문, 상태, 비어 있지 않은 번역, 필요한 변수를 검사합니다. 이후 승인할 때 다른 사람이 수정한 내용도 감지할 수 있도록 저장소의 현재 번역 파일도 확인합니다.

봇은 바뀌지 않는 스냅샷을 저장하고 SHA-256 해시와 검수 링크를 남깁니다. 이슈 요약이나 실시간 시트만 보지 말고 **그 스냅샷의 실제 내용**을 검수하세요. 제출 후보는 스냅샷이며, 시트는 미리보기 이후에도 바뀔 수 있습니다.

검수자는 원문 대비 의미와 문맥, 자연스러운 표현과 용어 통일, 필요한 경우 UI 길이와 발화감, 플레이스홀더·태그·줄바꿈 위치를 확인합니다.

수정할 내용이 있으면 시트를 고치고 `/work preview`를 다시 실행해 새 해시를 사용하세요. 미리보기 링크는 검수 자료이며, 병합 허가가 아닙니다.

## 5. 정확히 그 스냅샷 승인하기

**배정된 검수자만** 아래 예시를 미리보기의 전체 해시로 바꿔 댓글을 답니다.

```text
/work approve <sha256>
```

봇은 검수자 계정을 확인하고 시트를 다시 읽어 승인한 스냅샷과 일치하는지 검사합니다. 미리보기 이후 원문과 저장소 대상 파일이 그대로인지도 확인합니다. 시트나 대상 파일이 바뀌면 새 미리보기가 필요합니다. 정식 원문 테이블이 바뀌면 아래 절차에 따라 작업을 새로 배정해야 합니다.

검사를 통과하면 봇이 PR을 만듭니다. **직접 병합하지는 않습니다.** 시트의 `Approved` 표시나 일반적인 ‘좋습니다’ 댓글로는 이 명령을 대신할 수 없습니다.

관리자는 변경 사항을 검토하고 검사 통과 후 병합합니다. 그때까지 작업은 계속 예약됩니다. 제출 파일에 관한 논의는 해당 PR에 모아 최종 변경을 따라가기 쉽게 해 주세요.

신뢰할 수 있는 `reviewed-sheet` 정책은 PR을 기록된 작업 이슈와 승인 스냅샷에 대조합니다. PR 파일은 데이터로 읽고, 실행 코드는 신뢰된 기본 브랜치에서 가져옵니다. 수동 번역 PR, 승인 후 바뀐 제출 파일, 다른 파일을 끼워 넣은 제출은 거절합니다. 승인 후 봇 브랜치를 수정해도 검수받은 문장을 다른 내용으로 바꿀 수 없습니다.

## 6. 완료 처리하거나 예약 해제하기

PR을 병합하거나 닫은 뒤 관리자가 실행합니다.

```text
/work sync
```

병합된 PR이면 작업을 완료하고, 병합하지 않고 닫은 PR이면 예약을 해제합니다. 이슈 상태만 보고 판단하지 말고 봇의 확인을 보세요.

등록된 봇 PR은 GitHub의 종료 이벤트를 받으면 자동으로도 동기화합니다. 자동 실행이 끝나지 않았다면 `/work sync`로 맞춰 주세요. 열려 있는 PR에서는 검사 재실행도 요청합니다. PR은 만들어졌지만 검사 실행 요청이 실패한 경우에도 사용할 수 있습니다.

PR 생성 전에 작업을 취소하려면 관리자가 댓글을 답니다.

```text
/work release
```

열린 PR은 먼저 닫아야 예약을 해제할 수 있습니다. 같은 범위의 제출 두 개가 동시에 활성화되는 것을 막기 위한 규칙입니다.

## 명령어 표

| 명령어 | 실행할 수 있는 사람 | 결과 |
| --- | --- | --- |
| `/work assign` | 관리자 | 작업 내용과 원문 범위를 고정하고 예약합니다. |
| `/work preview` | 배정된 작업자·검수자, 관리자 | 검사한 뒤 검수용 스냅샷을 저장합니다. |
| `/work approve <sha256>` | 배정된 검수자 | 해당 스냅샷을 다시 확인하고 PR을 만듭니다. |
| `/work release` | 관리자 | 열린 PR이 없는 예약을 취소합니다. |
| `/work sync` | 관리자 | PR 상태와 예약 장부를 동기화합니다. |

## 게임 원문이 바뀌었을 때

게임 버전마다 새 문서를 만들 필요는 없습니다. 안정적인 원문 ID를 사용하면 보통의 원문 업데이트에서도 기존 번역을 이어갈 수 있습니다. 원문 행 추가와 변경 번역 검수는 [로컬라이제이션 안내](../../localization/README.md)의 저장소 갱신 절차를 따릅니다.

작업은 UI 테이블 또는 배역의 **원문 전체**가 고정된 상태로 배정됩니다. 승인 전에 그 정식 원문 테이블이 바뀌면, 배정된 키 자체가 그대로여도 가져오기를 중단합니다. 관리자는 열린 제출 PR을 닫고 기존 예약을 해제한 뒤, 시트 원문을 갱신하고 **새 작업 이슈**를 만듭니다. 자원자가 작성한 번역은 보존하면서 새 원문에 맞게 확인하고, 검수자는 새로운 미리보기를 검수합니다. 다른 원문 테이블의 작업은 계속할 수 있습니다.

실제 원문 ID가 없는 기획 행은 아직 가져오기 대상이 아닙니다. 개발자가 정식 원문 항목을 추가할 때까지 기획 영역에 두세요. 미래 콘텐츠를 넣기 위해 임의로 실제 ID를 만들거나 시트 전체를 제출하지 마세요.

## 관리자 설정과 한계

- 코드와 이슈 양식이 기본 브랜치에 병합된 뒤 작업 워크플로를 활성화합니다. 예약 장부는 `community-work-state`에 있습니다. 명령을 처리하는 동안 수동으로 수정하지 마세요.
- 저장소의 `GITHUB_TOKEN`을 사용하며, 장부·봇 브랜치 쓰기, 이슈 댓글, PR 생성에 필요한 권한이 있어야 합니다. Google OAuth 연결이나 개인 액세스 토큰은 필요하지 않습니다. Google 접근은 공개 CSV 읽기로 제한됩니다.
- 저장소 Actions 설정에서 GitHub Actions의 PR 생성을 허용합니다. 봇 계정과 실제 언어 검수자의 신원은 별도로 유지하세요.
- 봇이 만든 PR에서 일반 `pull_request` 워크플로가 자동 시작될 것이라고 기대하지 마세요. 가져오기 과정에서 후보를 먼저 검사하고, 봇 브랜치의 `check.yml`과 신뢰된 기본 브랜치의 `delivery-policy.yml`을 해당 PR 번호로 명시적으로 실행 요청합니다.
- 기본 브랜치에서 `check`와 커밋 상태 `reviewed-sheet`를 모두 필수 검사로 설정합니다. 정책 워크플로에는 이 상태를 게시할 권한이 필요합니다. 병합 전에 두 검사가 모두 성공했는지 확인하세요. 워크플로 파일을 만드는 것만으로 브랜치 보호가 적용되지는 않습니다.
- 예약 장부는 중복 배정을 막고, 필수 제출 정책은 수동 번역 PR이 배정을 우회하지 못하게 합니다. 두 기능 모두 Google 시트 편집 권한은 관리하지 않습니다. 편집자를 제한하고 원문 열을 보호하세요.

자동 검사는 구조 오류와 오래된 내용을 감지합니다. 번역 품질, 문맥, 기여자 약관, 게임에 적절한 내용인지 여부는 사람이 검토해야 합니다.
