# Задания на перевод: от назначения до отправки

Эталоном служит [английский оригинал](../CONTRIBUTION_WORKFLOW.md). Замечания о русских формулировках приветствуются.

Перевод и проверка выполняются в Google Таблицах. Задание в GitHub фиксирует объём, исполнителя и проверяющего, а также определяет, когда одобренный текст можно отправить в pull request (PR).

**Изменения в таблице не попадают в репозиторий или игру автоматически.** Бот переносит в PR точный снимок проверенного текста. Сопровождающий проекта проверяет и сливает PR, а разработчик добавляет результат в сборку игры.

Запись в списке заявителей или инструкция в таблице сама по себе не означает, что работа закреплена или результат одобрен.

Этот процесс предназначен для существующих строк интерфейса и **письменного перевода реплик озвучки**. Записи голоса, прослушивания, черновики новых реплик и текст без исходного ID готовятся отдельно. PR с переводом интерфейса или реплик должен создавать бот заданий. Ручной PR не позволяет обойти назначение и одобрение снимка.

Команды отправляются комментариями в назначенном GitHub issue задания. Для одобрения скопируйте все 64 символа после `Digest:` в ответе бота с предварительным просмотром и замените только `<sha256>` в примере. Команду оставьте на английском; не отправляйте буквальный текст `<sha256>` вместо хеша.

## Кто за что отвечает

| Участник | Обязанности |
| --- | --- |
| Переводчик | Переводит назначенный диапазон в таблице и запрашивает предварительный просмотр. |
| Проверяющий | Проверяет контекст, термины, естественность текста и сам снимок; одобряет его хеш со своей учётной записи GitHub. |
| Сопровождающий | Создаёт или проверяет задание, резервирует диапазон, управляет доступом к таблице, проверяет и сливает итоговый PR. |

Переводчик и проверяющий должны быть **разными пользователями GitHub**. Бот проверяет учётные записи и структуру файлов, но не определяет, насколько естественно звучит перевод.

Сам перевод можно полностью выполнить в Google Таблицах. Устанавливать Git, клонировать репозиторий и создавать свой PR не требуется. Для одобрения снимка проверяющему нужна собственная учётная запись GitHub. Если переводчику трудно пользоваться комментариями GitHub, сопровождающий может запросить просмотр за него.

## 1. Согласуйте небольшую задачу

Подайте обычную заявку переводчика через issue или создайте тикет поддержки в Discord. До начала работы согласуйте с сопровождающим язык, переводчика, проверяющего и объём.

Закрытая таблица заявителей — очередь приёма, а не реестр назначений. Не переносите из неё контакты и сообщения тикетов в публичные GitHub issues.

Создайте [issue по форме Translation work order](https://github.com/Epheria/Ebbtide-Community/issues/new?template=work_order.yml). Названия полей формы оставлены на английском:

| Поле | Что указать |
| --- | --- |
| Kind | `ui` или `voice-text` |
| Locale | Код языка репозитория, например `ru`, `ja` или `pt-BR` |
| Table or voice role | Имя существующей исходной таблицы или роли, без пути и расширения `.csv` |
| Contributor | Логин одного переводчика в GitHub, без `@` |
| Reviewer | Логин другого проверяющего в GitHub, без `@` |
| Spreadsheet URL | Адрес Google Таблицы для этой задачи |
| Sheet tab | Точное название вкладки |
| First key | Первый существующий исходный ключ, входящий в диапазон |
| Last key | Последний существующий исходный ключ, входящий в диапазон |

Диапазон включает **обе границы в порядке официального исходного файла**. Это не алфавитный порядок и не текущая сортировка строк в таблице. Максимум — 200 ключей на задание. Для реплик ключом служит идентификатор `file` из сценария, без `.wav` или `.flac`.

Одно задание охватывает один язык и одну таблицу интерфейса либо одну роль. Короткий диапазон проще проверять; он также уменьшает число конфликтов при изменении игрового текста.

## 2. Зарезервируйте работу до начала перевода

Сопровождающий пишет в issue:

```text
/work assign
```

**Дождитесь подтверждения бота.** Создание или закрытие issue, а также имя в ячейке не резервируют и не освобождают работу.

Бот сохраняет назначение в `registry.json` ветки `community-work-state`: фиксирует поля issue, точные ключи и хеш исходника. Он отклоняет пересечения с активным заданием того же типа, языка и таблицы или роли. Для разных языков можно работать с одинаковыми ключами.

Редактирование текста issue не меняет действующее назначение. Для изменения диапазона, документа, переводчика или проверяющего попросите сопровождающего освободить старую задачу и создать новое задание.

## 3. Переводите в таблице

Сопровождающий добавляет актуальные исходные строки и выдаёт исполнителям доступ к редактированию. Бот должен читать документ без входа в Google, но право редактирования следует ограничить участниками задачи.

Защитите ключи и английский оригинал, а переводчикам откройте только необходимые поля ввода. Не включайте редактирование для всех, у кого есть ссылка. Права Google и защищённые диапазоны настраиваются вручную; GitHub-бот ими не управляет.

Для интерфейса сохраняйте четыре столбца:

```text
key,en,translation,status
```

Используйте вкладку со строками **только одной таблицы интерфейса**, указанной в задании. Общий список нескольких таблиц подходит для справки, но не для прямого импорта. Бот сверяет все заполненные строки выбранной вкладки с этой исходной таблицей.

Заполняйте `translation`, используя только существующие значения `status`. Для импорта UI значение `status` должно быть пустым. Строки с `review` или `outdated` остаются на проверке. Пустой статус сам по себе не является одобрением: нужен отдельный этап проверки снимка.

Для письменного перевода реплик сохраняйте эти заголовки и их порядок:

```text
Take file,English source,Translation,Review status,Notes,Role,Situation,Tone,Current voices,Source readiness,Source file,Source record
```

Существующие японская, русская и корейская вкладки реплик используют этот формат. Бот выбирает точное значение `Role`, например `carrier_jet_pilot`, затем зарезервированные ключи `Take file`. Заполните `Translation`; после проверки установите `Approved` в `Review status`.

Одобренный текст сохраняется в `voice/translations/<locale>/<role>.csv` со столбцами `key,en,translation,status`. Импортируется только текст. Это не одобрение записи голоса и не подтверждение, что черновая реплика реализована в игре.

Для обоих видов заданий:

- Сохраняйте переменные, обязательные теги и обозначения переносов строк.
- Не меняйте ключ и английский текст: они должны точно совпадать с назначенным исходником.
- До запроса просмотра заполните все переводы зарезервированного диапазона.
- Работайте с ячейками как с текстом. Не используйте формулы для получения или составления перевода.
- Не добавляйте в рабочий документ или issue личные контакты, закрытые сообщения тикетов и файлы прослушиваний.

Если задача слишком велика, согласуйте её разделение или освобождение. Не оставляйте частично выполненную работу зарезервированной бессрочно.

## 4. Запросите и проверьте снимок

Назначенный переводчик, проверяющий или сопровождающий пишет:

```text
/work preview
```

Бот читает диапазон из публичного CSV-экспорта Google Таблиц. Он проверяет зафиксированный исходник, статусы, наличие переводов и обязательные переменные. Также проверяется текущий файл перевода в репозитории: это позволит заметить чужие изменения к моменту одобрения.

Бот сохраняет неизменяемый снимок, публикует его хеш SHA-256 и ссылку для проверки. Проверяйте **содержимое самого снимка**, а не только описание issue или живую таблицу. Именно снимок предлагается к отправке; таблица после его создания может измениться.

Проверяющий сверяет смысл и контекст с английским оригиналом, естественность и единообразие терминов, длину текста интерфейса или удобство произнесения, положение переменных, тегов и переносов строк.

Если нужны исправления, измените таблицу и повторите `/work preview`. Используйте новый хеш. Ссылка на просмотр — материал для проверки, а не разрешение на слияние.

## 5. Одобрите точный снимок

**Только назначенный проверяющий** пишет команду, заменив пример полным хешем из просмотра:

```text
/work approve <sha256>
```

Бот проверяет автора одобрения, повторно получает таблицу и требует совпадения со снимком. Он также проверяет, что исходник и целевой файл репозитория не изменились после просмотра. Изменение таблицы или целевого файла требует нового просмотра. Изменение официальной исходной таблицы требует нового задания по правилам ниже.

При успехе бот открывает PR, но **не сливает его**. Значение `Approved` в таблице или обычный комментарий «всё хорошо» не заменяют эту команду.

Сопровождающий проверяет разницу и сливает PR после успешных проверок. До этого работа остаётся зарезервированной. Обсуждайте предлагаемые файлы в соответствующем PR, чтобы было видно, откуда взялись итоговые изменения.

Доверенная политика `reviewed-sheet` сверяет PR с зарегистрированным заданием и одобренным снимком. Файлы PR читаются как данные; выполняется код доверенной ветки по умолчанию. Ручной PR с переводом, изменённый файл поставки или дополнительные файлы в переводческом PR отклоняются. Редактирование ветки бота после одобрения не позволяет подменить проверенный текст.

## 6. Завершите или освободите задачу

После слияния или закрытия PR сопровождающий выполняет:

```text
/work sync
```

Слитый PR завершает задачу; закрытый без слияния освобождает её. Проверяйте подтверждение бота: статус issue сам по себе не меняет резервирование.

Координатор также синхронизирует зарегистрированный PR бота по событию закрытия GitHub. Если автоматическая обработка не завершилась, используйте `/work sync`. Для открытого PR эта команда повторно запрашивает проверки, в том числе если их запуск не удался после создания PR.

Чтобы отменить назначение до появления PR, сопровождающий пишет:

```text
/work release
```

Перед освобождением открытый PR необходимо закрыть. Это не даёт двум активным поставкам занять один диапазон.

## Справочник команд

| Команда | Кто выполняет | Результат |
| --- | --- | --- |
| `/work assign` | Сопровождающий | Фиксирует задание и резервирует исходный диапазон. |
| `/work preview` | Назначенный переводчик, проверяющий или сопровождающий | Проверяет и сохраняет снимок для просмотра. |
| `/work approve <sha256>` | Назначенный проверяющий | Повторно проверяет точный снимок и открывает PR. |
| `/work release` | Сопровождающий | Отменяет резервирование, если нет открытого PR. |
| `/work sync` | Сопровождающий | Согласует состояние PR с реестром. |

## Когда меняется текст игры

Не создавайте новый документ для каждой версии игры. Стабильные ID позволяют сохранять переводы при обычных обновлениях исходника. Добавляйте исходные строки через процесс обновления репозитория и отмечайте изменённые переводы для проверки, как описано в [руководстве по локализации](../../localization/README.md).

Назначение фиксирует исходник **всей таблицы интерфейса или всей роли**. Если до одобрения эта официальная таблица изменится, импорт остановится, даже когда зарезервированные ключи не затронуты. Сопровождающий закрывает открытый PR поставки, освобождает старое задание, обновляет исходные строки в таблице и создаёт **новый issue задания**. Сохраните уже выполненный перевод волонтёра, сверяя его с обновлённым исходником; проверяющий затем проверяет новый снимок. Задания для других исходных таблиц могут продолжаться.

Плановая строка без реального исходного ID ещё не готова к этому импорту. Оставьте её в планах, пока разработчик не добавит официальную исходную запись. Не придумывайте рабочие ID и не отправляйте всю таблицу ради будущего контента.

## Настройка для сопровождающих и ограничения

- Включайте процесс после слияния его кода и формы issue в ветку по умолчанию. Реестр хранится в `community-work-state`; не редактируйте его вручную во время выполнения команд.
- Используется `GITHUB_TOKEN` репозитория с правами для записи реестра и ветки бота, комментариев к issues и создания PR. Подключение Google OAuth и личный токен не нужны. Доступ к Google ограничен чтением публичного CSV.
- В настройках Actions разрешите GitHub Actions создавать PR. Бот и человек, проверяющий язык, должны оставаться разными участниками.
- Не рассчитывайте, что PR от бота запустит обычные процессы `pull_request`. Импортёр проверяет файлы до создания PR и явно запускает `check.yml` для ветки бота и `delivery-policy.yml` из доверенной ветки по умолчанию для этого номера PR.
- Защитите ветку по умолчанию двумя обязательными проверками: `check` и статусом коммита `reviewed-sheet`. Процесс политики должен иметь право публиковать этот статус. До слияния проверьте успешное завершение обеих проверок. Само создание файлов workflow не настраивает защиту ветки.
- Реестр предотвращает пересекающиеся назначения, а обязательная политика поставки не позволяет ручным PR обойти их. Ни один из этих механизмов не управляет правами Google Таблиц. Ограничивайте редактирование и защищайте исходные столбцы отдельно.

Автоматические проверки находят структурные ошибки и устаревшее содержимое. Качество перевода, контекст, условия участия и пригодность материала для игры остаются ответственностью людей.
